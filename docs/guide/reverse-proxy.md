# Reverse proxy

wedge can pass requests for some paths to application servers (upstreams)
and serve everything else as static files.

## Upstreams and routes

```toml
[server]
listen = ["0.0.0.0:80"]
default_vhost = "shop"

[[upstream]]
name = "api"
servers = ["127.0.0.1:3000", "127.0.0.1:3001"]
health_path = "/healthz"

[[vhost]]
name = "shop"
root = "/srv/shop"                # static files for everything else
hosts = ["shop.example.com"]

[[vhost.proxy]]
path = "/api/"
upstream = "api"
max_body_bytes = 1048576          # 1 MiB uploads
```

- `servers` are IP:port pairs. Host names are not accepted, so a DNS change
  cannot redirect traffic (DNS rebinding).
- `path` is a prefix on segment boundaries: `/api` and `/api/` both match
  `/api` and `/api/orders`, but not `/apix`. The longest matching prefix wins.
- A vhost may have no `root`; then requests that match no route get 404.
- Requests are passed to the upstream with their path and query unchanged.

## Load balancing and health

Requests go to the servers in turn (round-robin), skipping servers that are
down:

- With `health_path`, wedge sends `GET <health_path>` to every server every
  `health_interval_secs` (default 10). A 2xx or 3xx answer means healthy.
- Connection failures count too. After `unhealthy_after` consecutive failures
  (default 2) a server is skipped; one success brings it back.
- Without `health_path`, a skipped server is tried again after
  `health_interval_secs`.

If no server is up, the client gets `503`. A request that could not connect
is retried on the next server only for `GET`, `HEAD` and `OPTIONS` without a
body; other requests are never replayed.

## Timeouts and errors

```toml
[[upstream]]
name = "slow-reports"
servers = ["10.0.0.20:8000"]
connect_timeout_secs = 5          # opening the TCP connection
response_timeout_secs = 120       # waiting for the response head, and the
                                  # longest pause while the body streams
```

wedge's own error pages are generic (`502 Bad Gateway`,
`503 Service Unavailable`, `504 Gateway Timeout`) and never name the
upstream; the details go to the error log. Error pages generated by your
application pass through unchanged.

## Headers wedge changes

Towards the upstream, wedge:

- removes hop-by-hop headers (`Connection`, `Keep-Alive`, `TE`, `Upgrade`,
  `Transfer-Encoding`, `Proxy-Authorization`, ...) and every header the
  client names in `Connection`;
- replaces `X-Forwarded-For` with the client's address, and sets
  `X-Forwarded-Proto` (`http`/`https`) and `X-Forwarded-Host`;
- removes client-supplied `X-Real-IP`, `X-Forwarded-Port` and `Forwarded`,
  which clients could use to fake their address;
- keeps `Host` as the client sent it.

If wedge sits behind a load balancer, list it so its `X-Forwarded-For` chain
is extended instead of replaced:

```toml
[server]
trusted_proxies = ["10.0.0.0/8", "192.168.1.5"]
```

Towards the client, hop-by-hop headers from the upstream are removed. wedge's
default security headers are added only where the application did not set
them; headers you set in `[vhost.headers]` always win.

## Paths that would escape the route

A path such as `/api/../admin` or `/api/%2e%2e/admin` matches `/api/` in
wedge but would reach `/admin` on the upstream. wedge refuses such paths with
`400`, along with encoded slashes or backslashes and NUL bytes.

## Not supported yet

TLS to upstreams, WebSocket (`Upgrade`) tunnelling and HTTP/2 to upstreams
are planned for later releases. Run the upstream on a private address or the
loopback interface.
